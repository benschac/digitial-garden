I'm building Snap to Post to help someone turn the items in front of them into researched listing drafts. The starting point is a camera: photograph an item, collect evidence about what it is, and use that evidence to help prepare a listing.

The experience I want is straightforward. Someone should be able to photograph one item and move on to the next while the application works in the background. They should see useful information as it becomes available, with a clear distinction between an initial guess and an identity supported by research.

That objective shapes the system. A photograph can give us a category or a likely identity. Text on a label, a barcode, another view, and product research can help narrow it down. Those clues arrive at different times. The application needs to keep making progress while there is still more to learn.

This post follows that work from the camera to the listing draft, then looks at one coordination problem in detail: deciding when remote identification requests can run. That's where I use Effect to combine a limit on concurrent work with an ordering rule for each item.

## What we're trying to help the seller do

Preparing a listing involves more than taking a photograph. Someone needs to identify the item, work out which details are supported, and describe what they're selling. A broad category can be useful, but an exact model or variant needs stronger evidence.

Consider a seller photographing two items. For the first, they take an overall view and then a closer photograph of a label. While the application processes those images, they begin photographing the second item. This is the kind of session the system needs to support.

For the seller, there are two kinds of progress. They can keep capturing items, and the application can keep improving the information attached to items they've already captured. If every new photograph had to wait for identification, product search, and listing generation to finish, those two activities would become one long sequence of waits.

The objective is to turn captured evidence into useful listing information while letting the seller continue. That also means preserving uncertainty: seeing a familiar shape or reading a brand name doesn't establish an exact model.

The flow described here produces a researched draft in the application. Publishing that draft to a marketplace is a separate step.

## What we're building at a high level

Snap to Post has a React Native client and a backend. The phone handles the camera, on-device perception, and microphone capture. The backend uses selected photographs, observations, and available seller narration to identify the item, retrieve product evidence, and generate listing information. ElevenLabs Scribe turns the seller's speech into text that can inform the draft.

The work falls into three connected stages:

1. **Collect evidence.** Capture useful views and gather observations such as recognized text and barcodes. On-device models can also provide an early category or identity candidate.
2. **Identify and research.** Send selected images and available signals to the backend for visual identification, then use the resulting clues to search for relevant product information.
3. **Build the draft progressively.** Compare the candidate with retrieved evidence and available seller narration, then send identity, metadata, condition, market, and listing-text updates back to the item.

These stages describe the flow of information. They don't require the entire application to wait at each boundary. Local perception can overlap with remote identification, and a useful identity candidate can reach the seller while research is still underway.

That distinction is central to the design: the first useful answer and the finished researched draft have different completion points.

## Follow one item through the system

Start with a selected photograph. VisionCamera supplies the image, and React Native ExecuTorch runs on-device perception, including object detection, optical character recognition (OCR), and image classification. An optional local vision-language model can contribute a more detailed identity.

Those results have different roles. Local classification can update the item's candidate on the phone. Recognized text and a barcode can become evidence for the backend. The local classification and vision-language results aren't uploaded as the server's visual-classification input.

Saving the photograph starts OCR and progressive identification independently. We can send the images with whatever OCR evidence is available at that moment. Useful text discovered afterward can request a refinement. Waiting for every local model would delay work that can already begin.

The mobile client uploads one to three selected JPEG views of the same item to `/v1/identify`, together with available OCR and barcode signals. Session, item, and image identifiers associate the request with its owner. The backend receives selected still-image evidence; the live camera feed stays on the phone.

The backend validates the upload and admits it within its provider budget. A visual model receives the image bytes and a prompt containing the client observations. A valid partial candidate can be sent back before the full model output is complete.

Once visual identification returns, the backend builds a text query from the supported identity, OCR, barcode, and variant clues. Exa retrieves product-page URLs, titles, and text highlights. This search uses text evidence rather than the original image bytes.

The seller can also describe the item aloud. The phone captures microphone audio with `expo-audio` and streams it directly to ElevenLabs Scribe over a WebSocket, using a short-lived speech token supplied by the backend. Partial and committed transcripts return to the phone, and transcript updates go through the oRPC control API associated with the captured item. Available final narration gives the listing resolver seller-supplied context, such as condition or included accessories. Speech capture can overlap with the image and research work.

A second model call compares the candidate with that retrieved evidence and available final seller narration. It resolves the identity and drafts listing information. The identity can remain inferred, become verified, or be marked conflicted; OCR and search text are treated as untrusted evidence throughout.

The return path has two parts. The upload's HTTP stream carries acceptance and the visual-identification result, or an error. A separate control WebSocket carries early candidates and later research and listing patches. Finishing the upload request therefore doesn't mean the listing is finished.

The seller can receive useful information at several points in this flow. A local category, a remote identity candidate, and a researched draft each answer a different question. Keeping their source and certainty visible lets the application show progress without presenting every intermediate result as settled fact.

## Why this becomes a coordination problem

Now return to the session with two items. The first item is waiting for a remote response. The seller has taken another view of it and has also started capturing the second item.

The system has several decisions to make. Can the second item begin identification? Should new evidence for the first item start another request immediately? What happens if the seller resets the session while a request is waiting or running?

Allowing every request to start immediately would leave active remote work without a defined limit. Making all requests wait behind one another would prevent independent items from progressing together. We need to express both shared capacity and ownership of an individual item.

The mobile remote queue has two rules:

- **Independent items can run concurrently, within a limit.** A queue instance defaults to four active remote identification tasks.
- **Submitted tasks for the same item run one at a time.** A second task for item A waits for A's current task to settle, even when shared capacity is available.

There is also a decision before submission. While an item's current identification cycle is in flight, the caller keeps its latest pending snapshot. If newer evidence arrives again, it replaces that pending snapshot. This coalesces updates rather than retaining a remote request for every intermediate observation.

The caller decides which evidence to process next. The queue decides when a submitted remote task may begin. Keeping those responsibilities explicit helps explain both the implementation and its limits.

## Where Effect fits

Effect lets us describe an asynchronous task, put execution rules around it, and then run it. In this queue, the rules are semaphore permits: one permit for the item and one from the shared pool of remote capacity.

The item permit comes first. A task waiting for item A doesn't consume a shared slot that item B could use. Once both permits are available, the queue calls the submitted Promise-returning function. When that task settles, the permits are released.

The rest of the application still awaits a Promise. The remote identification function keeps its existing interface. Effect supplies the permit coordination inside the queue; the application supplies item ownership, the concurrency setting, cancellation policy, and bookkeeping.

The boundaries matter here. The queue covers the mobile identification request. Backend research can continue after that request returns, and on-device inference has its own coordination. The caller also waits for classification, remote identification, and local vision-language work to settle before considering the next pending snapshot for that item. A remote slot can be free while that item's overall cycle is still waiting.

This gives us a specific problem to examine next. With two shared slots, submit A1 and A2 for item A, then B1 for item B. We want A1 and B1 to run together while A2 waits. Following that example through permit acquisition, cancellation, and failure will show exactly what Effect is doing—and which decisions still belong to our code.
