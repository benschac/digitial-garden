## What is Quick Catalog?

Quick Catalog solves my problem of cataloging the hundreds of different items in my home.

Quick Catalog is [open source on GitHub](https://github.com/benschac/snap_post) and a work in progress.

This becomes useful when I'm:

- Getting renter's insurance and need an itemized list of my belongings, with proof of what I own.
- Traveling with checked bags.
- Looking to sell items on multiple platforms.

The process of manually looking up and tagging each item, then describing its condition and appearance is really error-prone, tedious, and time-consuming.

## What makes it better?

The goal is speed and less tippy-tappy on the keyboard.

An opportunity in consumer AI that I think is truly magical is that we can interface with our technology without needing to use our fingers. A feeling of magic that Steve Jobs is articulating, but also kind of makes me feel like I'm living in a Jetsons episode.

Everything can be done by just pointing your phone camera and speaking to the app in real time. We can tell the app every imperfection, ding, or unique property of the item, and it'll automatically be added to the listing. Tasks are handled in parallel and in the background, so everything feels especially snappy.

## High Level Implementation

The phone turns a continuous camera feed into a small set of item evidence. It finds an object, chooses useful photographs, reads visible text, and can show a provisional local identity. The backend uses selected photographs and available OCR/barcode observations to identify the product, retrieve supporting pages, and assemble a listing draft.

There are three useful boundaries to follow:

| Boundary | Artifact leaving it | What it enables next |
| --- | --- | --- |
| Live camera → captured item | Saved JPEG views, item/image IDs, and collected observations. | Local models and remote identification can work on the same item while capture continues. |
| Phone → backend | Selected JPEGs, JSON OCR/barcode signals, and session/item/image headers. | Remote visual identification gets both image evidence and machine-read clues without waiting for the optional local VLM. |
| Identification → research | A structured identity candidate, supporting signals, and a text search query. | Exa retrieves product evidence; a resolver combines it with the candidate and available seller narration. |

Here, **artifact** means the evidence handed from one stage to the next. The device-to-backend artifact is a multipart request, not a single model-generated JSON object. The local candidate shown in the interface is a separate output.

Part one follows that handoff step by step. Parts two and three go deeper into request coordination and backend research. The tool inventory below identifies who owns each part.

## Step by step: from the camera to a researched item

Follow one captured item through the system. The bottle examples below illustrate payload shapes; they are not a recorded capture or measured timing trace.

### 1. Find an object and decide which view to keep

The live camera produces frames continuously, but the app only analyzes selected frames. **SSDLite 320 + MobileNet V3 Large** returns bounding boxes, labels, and confidence scores. App code combines those detections with image-quality and motion checks to track objects and decide when to capture a photograph. Eligible frames also enter a separate OCR worker, and later camera callbacks collect its completed results.

There are two decisions here: **whether to analyze a frame**, and **whether to submit it for OCR**. A sampled frame can contribute bounding boxes, quality scores, and motion information without triggering text recognition. OCR submissions have their own timing, quality, and motion checks.

Raw camera frames stay out of React state. Legend State holds the compact item and capture state used by the interface, while Reanimated shared values carry frequent overlay and feedback updates.

Frame lifetime matters at this boundary. Whether a frame is analyzed or skipped, the application must release it. A selected photograph has a different lifetime: it is saved as JPEG evidence with a smaller preview that can be used while capture continues.

OCR introduces a harder problem. Reading a label takes time, and the camera can deliver more frames before that work finishes. Submitting every frame would create a queue of increasingly old views.

### 2. Read visible text without building a frame backlog

Quick Catalog uses a fork of React Native ExecuTorch with a native OCR worker running **CRAFT followed by the English CRNN recognizer**. The worker runs live OCR separately from the camera analysis callback, allowing that callback to continue with detection and quality analysis between submissions.

The application first gates submissions using timing, quality, and motion checks. For frames that pass those checks, the worker has a small scheduling rule: **one active frame and at most one pending frame**. A new submission replaces the pending frame if one is already waiting.

Frame B never runs. The worker favors the newest eligible view when it becomes available for more work.

Replacing waiting work keeps the backlog bounded without requiring the active inference to stop.

The OCR result is a list of text detections, each with a bounding box, recognized text, and score. App code filters low-confidence detections, orders the remaining text by position, and merges unique lines into the current item. For example, it might retain `OWALA` and `32 OZ` in `visibleLabelText`. The local extraction currently leaves `otherProductIdentifiers` empty; it does not turn those lines into structured brand or model fields.

The fork exposes three operations for this path: `submitFrame`, `takeLatestFrameResult`, and `resetFrameWorker`. The camera path submits eligible frames and polls for completed results on subsequent analyzed frames. Each result includes its item association and timing information.

#### Keep pixels and results attached to the right work

Moving OCR to another thread introduces two ownership questions: how long the pixels remain valid, and whether the result still belongs to the current work.

For the pixels, the fork secures an owned copy during submission. The worker can then use those pixels after the camera frame is released. This has a cost: copying and preparing the image still happen before the background inference, so submitting work is not free.

For results, the worker uses a generation counter. A job records the generation in which it was submitted. Resetting the worker advances that counter and clears pending work and the latest stored result. When active inference finishes, the worker only publishes its result if the generation still matches.

A reset therefore invalidates old work without interrupting the native inference already running. Item ownership is also checked when the application consumes OCR results. Finishing an operation doesn't automatically make its output relevant to the current item.

Live OCR and OCR on saved photographs share an inference mutex, which permits one inference at a time. A saved photograph can wait behind live inference. The background worker bounds waiting live frames; it doesn't eliminate contention for the model.

These tradeoffs need physical-device measurements: frame throughput, dropped frames, submission and copy time, captured-photo OCR latency, memory, and thermals. The scheduling behavior explains how the application avoids a growing live-frame backlog. It doesn't establish a measured speedup.

### 3. Start independent work from the saved photograph

Saving a photograph starts **CRAFT + English CRNN photo OCR** and progressive identification independently. Within identification, **EfficientNet V2 S** classifies a saved image while the remote request can begin with the evidence already available. **LFM2.5-VL-450M** waits for classification to settle before using an available category hint with the selected photographs.

#### Turn a broad category into a provisional local identity

EfficientNet produces scores for ImageNet labels. The app takes its top five results, groups recognized labels into item categories, and sums their scores. Several bottle labels can therefore contribute to the same `bottle` category. If no mapped category meets the threshold, classification supplies no new category hint.

When LFM is ready, it receives the selected photographs and the classifier's category, or an existing candidate's category when classification provides none. Its task is to make that description more specific using visible evidence. The prompt asks for a short label, broad color, readable capacity, and visible text. OCR's extracted strings are not injected into this local VLM prompt; LFM reads the photographs itself.

For an illustrative response with the label `Owala FreeSip bottle`, color `purple`, and capacity `32 oz`, the app can construct this local candidate:

```json
{
  "candidateId": "item-0:image-1:local-lfm2-5-vl-450m",
  "level": "product_family",
  "category": "bottle",
  "productName": "Owala FreeSip bottle",
  "variant": "32 oz · purple",
  "confidence": 0.55,
  "provenance": [{ "sourceId": "image-1", "sourceType": "visual_observation" }]
}
```

This example shows the application's candidate shape, not a recorded model result. For this compact-label response path, `0.55` is an app-assigned confidence value, not a calibrated probability from LFM. The candidate is held in the item's identity state with source `local-vlm`. The image IDs record which views support it. The parsed color and capacity become the candidate's `variant`; the OCR extraction remains separate item evidence.

That gives us a concrete on-device result: **saved views, any collected OCR/barcode evidence, and a provisional identity candidate for the interface**. These are held in the capture and identity state, rather than combined into a single model response. The candidate can improve as work completes, and the optional LFM path can be skipped.

### 4. Package the evidence for the backend

The upload is built from the saved views and the evidence available for that request. It can leave the phone before the local identity candidate above exists. The current endpoint is `POST /v1/identify`, with a multipart body:

| Request part            | What the phone sends                                                                                                                                 |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `images`                | One to three selected JPEG files, attached as repeated form fields named `images` with filenames such as `view-1.jpg`. Live frames are not uploaded. |
| `signals`               | A JSON string containing the OCR request, available OCR extraction, and an optional detected barcode.                                                |
| `X-Snap-Session-Id`     | The capture session ID.                                                                                                                              |
| `X-Snap-Item-Intent-Id` | The item being identified, such as `item-0`.                                                                                                         |
| `X-Snap-Image-Id`       | The newest selected capture's ID, used to associate the request and its results.                                                                     |

The header names still use `Snap` in the current implementation. With the illustrative OCR lines above and no barcode, the `signals` field is:

```json
{
  "ocr": {
    "requested": true,
    "triggers": ["selected_stable_frame"],
    "extraction": {
      "visibleLabelText": ["OWALA", "32 OZ"],
      "otherProductIdentifiers": []
    }
  }
}
```

If OCR has not produced useful text yet, `extraction` is omitted. If a barcode was detected, `signals.barcode` carries its `format` and `rawValue`, and the OCR triggers also include `barcode_detected`. A detector label in the app's text-heavy category set adds `text_heavy_category`.

The local candidate JSON is **not a field in this upload**. Detector boxes, classifier scores, and LFM's generated label stay on the phone; the backend receives the selected photographs and OCR/barcode observations. Useful text from photo OCR can request another identification pass with updated evidence.

This lets the first request begin without waiting for every local model. It also creates an important distinction between showing progress and finishing an item's current processing cycle. The caller still waits for classification, remote identification, and local vision-language work to settle before processing that item's next pending snapshot. A useful result may already be visible during that wait.

The backend's research and listing updates can continue after the initial identification request returns.

#### Why this artifact is useful

Each part answers a different question for the next stage. The JPEGs preserve appearance and readable details that local extraction may have missed. OCR supplies literal retrieval clues such as `OWALA` and `32 OZ`. A barcode supplies an exact observed identifier to cross-check against the photographs. The headers associate the work with a session, item, and captured view as results arrive asynchronously.

The phone does not have to settle the exact product identity before this handoff. It can send useful evidence now and request a refinement when more text becomes available. The backend can inspect the photographs for itself instead of depending on the optional local model's label.

### 5. Turn photographs and observations into a research query

The API passes the selected image bytes and client signals to the remote visual model through the AI SDK. Google's Gemini Flash fills this role in the checked-in configuration: the source default is `google/gemini-3.8-flash`. The evidence resolver uses the same default in a separate call. Both are configurable; these defaults do not establish which model a deployed server uses.

The visual prompt asks for a structured identity candidate first, then supporting signals: visible text, attributes, OCR fields, and a proposed search query. A valid partial candidate can reach the phone before the full output finishes. The prompt treats client OCR as observed text to check, and the barcode as a possible identifier to verify against the item. Neither establishes the physical item's condition.

Once visual inference finishes, the service merges its OCR with the phone's extraction and builds a text query from the available brand, product, model, variant, capacity, color, barcode, and visible-text clues. This is where a broad observation such as `bottle` can become a more specific research request. Local OCR contributes searchable words without having to correctly parse them into a verified brand or model on the phone.

Exa receives that **text query**, not the photographs. It returns product-page URLs, titles, and text highlights. The resolver then receives the candidate, signals, retrieved evidence, and any final seller narration available for the item. That second model call works with structured and text evidence rather than the original image bytes, and streams listing information back as it develops.

The artifact changes at each stage: **image evidence → identity candidate and search clues → retrieved sources → researched listing fields**. The benefit is a clear input for each job: visual identification interprets the photographs, search finds supporting pages, and resolution compares those sources with the observed item and seller's account.

### 6. Overlap independent work and return useful results early

The system has several opportunities for parallel work, but the ordinary research path has an order: **visual identification → Exa search → evidence resolution**. Exa needs the query built from identification, and the resolver needs the retrieved evidence.

| Work that can overlap | Why it can start independently |
| --- | --- |
| Saved-photo OCR, local classification, and remote identification | They can begin from the saved photograph and evidence already available. The remote request does not wait for the local VLM. |
| Capture of another item and research on the previous item | Research continues in the background; the mobile queue allows independent items to progress within its capacity limit. |
| Barcode research and visual identification | A separate barcode lookup can search from the observed code. The later research path can reuse a matching cached barcode result. |
| Visible feedback and remaining inference/research | Partial candidates and listing updates can be delivered before the corresponding work is complete. |

The upload's HTTP response uses NDJSON to report acceptance and the visual-identification result or an error. The oRPC control WebSocket carries early candidates and subsequent evidence and listing patches. Completing the upload response therefore does not mean the listing is finished.

This organization lets the phone keep capturing while the system enriches earlier items. It also lets the interface show a useful category or candidate before the final listing is ready. Those are scheduling and delivery properties of the implementation; measuring their effect on latency still requires a device trace.

## Next: keep several items moving

The native OCR worker handles incoming frames. Outgoing identification requests need a separate policy: independent items should be able to progress together, while requests for the same item run one at a time and total active work stays bounded.

That's where Effect enters Quick Catalog. ExecuTorch runs the local models; Effect supplies permit coordination inside the mobile remote-request queue. In part two, we'll follow two requests for item A and one for item B through that queue, including what happens when work fails or is cancelled.
