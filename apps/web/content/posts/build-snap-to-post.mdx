## Why I'm building Quick Catalog

Cataloging the hundreds of items in my home means photographing each one, looking up what it is, and describing its condition. That work is tedious whether I'm preparing an inventory for renter's insurance, tracking what goes into checked bags, or listing items for sale.

[Quick Catalog](https://github.com/benschac/snap_post) is my attempt to make that easier: point the phone camera at an item and describe it aloud, including any dings or other details worth recording. The goal is less tippy-tappy on the keyboard.

This post follows what happens on the phone: **choose useful photographs, read visible labels, and send available evidence to the backend.** The main challenge we’ll tackle is keeping text recognition from falling behind the camera.

## Take useful photographs automatically

With automatic capture enabled, you point the camera at an item and hold it steady; the app takes useful photographs without a shutter tap for each one. Automatic capture is on by default, and a manual mode is available.

The camera produces frames continuously. Most only need to exist long enough for the app to decide whether they're useful. A photograph is different: it's a saved view that the app can keep working with after the camera moves on.

[VisionCamera](https://github.com/margelo/react-native-vision-camera) supplies both. The app analyzes selected frames with an object detector running through [React Native ExecuTorch](https://docs.swmansion.com/react-native-executorch/). The detector, [SSDLite 320 with MobileNet V3 Large](https://docs.pytorch.org/vision/stable/models/generated/torchvision.models.detection.ssdlite320_mobilenet_v3_large.html), returns an object's location, label, and confidence score.

The detector’s boxes, labels, and scores feed object tracking. The capture policy looks for a stable tracked object, sufficient image quality, low motion, enough time since the last capture, and a view different from those already saved. When those checks pass during an active automatic-capture session, the app requests a separate photograph and saves a JPEG with a smaller preview.

That makes object detection part of the local evidence pipeline: **detect and track → check the view → take a photograph → run OCR and backend identification.** Its boxes and scores stay on the phone, but its capture decisions help determine which photographs the backend receives.

Every camera frame is released after use, including frames skipped by the sampling policy. The interface receives compact observations rather than raw frames.

Reading a label takes more work than deciding whether a view is useful. If the app submitted every frame for text recognition, it could spend its time reading views the user had already moved past.

## Read labels without falling behind

Optical character recognition (OCR) turns text in an image into strings the app can use. Quick Catalog does this in two steps: **[CRAFT](https://github.com/clovaai/CRAFT-pytorch) finds the text regions, then an [English CRNN recognizer](https://huggingface.co/software-mansion/react-native-executorch-recognizer-crnn.en) reads them.**

Live OCR runs in a native background worker in the app's [React Native ExecuTorch fork](https://github.com/benschac/react-native-executorch). This lets the camera callback continue with detection and quality analysis between OCR submissions.

The app only submits a frame when enough time has passed since the last submission, image quality is sufficient, and motion is low. Even then, frames can arrive faster than OCR finishes.

The worker handles that with one rule: **one active frame and at most one waiting frame. A newer submission replaces the waiting frame.**

Suppose OCR is reading frame A. Frame B arrives and waits. If frame C arrives before A finishes, C replaces B. When A finishes, the worker starts C; B never runs.

<Callout title="How to read this animation" variant="editorial">

- **Object detector — find the object.** SSDLite returns boxes, labels, and scores from sampled live frames.
- **Capture controller — decide when to photograph it.** App code tracks the object and checks stability, quality, motion, cooldown, and duplicate views. Passing those checks in automatic mode requests a photograph; its saved JPEG continues into the next diagram.
- **OCR models — find and read text.** CRAFT locates text regions; English CRNN reads the words. The app chooses eligible frames and supplies an owned pixel copy.
- **OCR worker — keep work current.** App scheduling keeps one active frame and one waiting frame. While A runs, C replaces waiting B. When A finishes, C starts.

Later camera callbacks collect completed OCR results for item-ownership checks. Every camera frame is released. The capture and OCR paths can progress independently; this illustrates the current fork's scheduling, not measured timing.

</Callout>

### Replace waiting work

The worker stores the waiting job in a single `pending_frame_` slot. Assigning a new job replaces whatever was waiting there. The active job continues running.

Here is the relevant C++ excerpt. Before this code runs, the frame's pixels have been copied and converted into image data owned by the job:

```cpp
{
  std::scoped_lock lock(frame_worker_mutex_);

  if (frame_worker_stopping_ ||
      generation != frame_worker_generation_) {
    return 0;
  }

  replacedPendingFrame = pending_frame_.has_value();

  pending_frame_ = FrameJob{
      itemIndex,
      generation,
      std::chrono::steady_clock::now(),
      std::move(bgr),
      orientation};
}

frame_worker_condition_.notify_one();
return replacedPendingFrame ? 2 : 1;
```

The lock protects the shared slot while it's updated. `notify_one()` wakes the worker so it can pick up waiting work. The generation check rejects submissions from work that has been reset.

This bounds the live-frame backlog even when OCR is slower than the incoming frames.

### Keep the pixels alive and discard stale results

Moving OCR off the camera callback creates two problems the queue alone doesn't solve.

**The worker needs its own pixels.** The camera frame is released after its callback, so the worker takes an owned copy during submission. Copying and preparing that image still cost time on the submission path.

**A completed result may be out of date.** Each job records the worker's current generation number. Resetting the worker advances that number and clears waiting work and the stored result. Active inference can finish, but its result is only published if the generation still matches. The app also checks which item owns the result before applying it.

A later sampled camera callback collects the latest completed result and passes it to the React Native runtime. App code filters low-confidence text, orders it by position, and merges unique lines into the item. For our bottle, that might produce `OWALA` and `32 OZ` in `visibleLabelText`. These are observed strings; the phone hasn't established a verified brand or model from them.

### What the worker still costs

Live OCR and OCR on saved photographs share a lock that allows one inference at a time. A saved photograph can therefore wait behind live OCR, even though the live queue stays small.

The bounded queue explains how the app avoids accumulating old frames. Its effect on responsiveness still needs physical-device measurements, including dropped frames, image-copy time, photo OCR latency, memory use, and heat.

## From a saved photograph to an upload

Saving a photograph starts photo OCR and remote identification with the evidence already available. Photo OCR gets another opportunity to read labels; useful new text can request another identification pass.

<Callout title="What happens to the saved photograph" variant="editorial">

- **Photo OCR — read the labels.** CRAFT finds text regions in the saved photo; English CRNN reads them into strings such as `OWALA` and `32 OZ`.
- **Backend handoff — send available evidence.** App code uploads selected JPEGs and available OCR/barcode observations. The remote visual model examines that evidence to propose an identity.
- **Item on phone — show the results.** App code updates the displayed identity and label text. Useful new photo OCR can request another identification pass.

The upload can start before OCR finishes. Late live OCR needs a later identification trigger, and a pending refinement can wait for the current item cycle to settle. The illustrated order is not measured timing.

</Callout>

<Callout title="Provisional labels on the phone" variant="editorial">

The detector and local classifier can supply provisional category labels while backend identification runs. Those predictions stay on the phone; the detector also feeds the automatic-capture policy described above.

An iPhone capture trace from September 3 recorded a detector category at **69 ms** after the photograph was requested, a classifier category at **211 ms**, and the first remote candidate at **5.25 seconds**. On another view of the mouse, the classifier corrected the detector’s “smartphone” label to “computer mouse.” The local vision-language model was unavailable in that session.

These are candidate-event timings, not measurements of when text appeared on screen. The first photograph had been superseded before its remote result arrived. The recording demonstrates useful early category feedback in that session; it does not establish typical latency or the richer local model’s benefit.

</Callout>

The initial upload does not wait for those predictions. However, the current per-item loop waits for local classification, remote identification, and local vision-language work to settle before processing a pending replacement. Slow local inference can therefore delay the next request for the same item. Part two examines that coordination.

## Send the evidence to the backend

The phone sends **selected photographs and available OCR or barcode observations**. Early identification prefers a small preview, targeted at 320×320; after item finalization, it can use the larger saved photograph, targeted at 1024×768, when the file fits the upload limit. The local identity label stays on the phone, along with detector boxes and classifier scores. The backend examines the photographs for itself.

The request goes to `POST /v1/identify` as a multipart upload:

| Part            | Contents                                                                      |
| --------------- | ----------------------------------------------------------------------------- |
| `images`        | One to three selected JPEGs.                                                  |
| `signals`       | JSON containing the OCR request, any extracted text, and an optional barcode. |
| Request headers | Session, item, and image IDs to associate results with the right capture.     |

For the bottle example, the `signals` field could contain:

```json
{
  "ocr": {
    "requested": true,
    "triggers": ["selected_stable_frame"],
    "extraction": {
      "visibleLabelText": ["OWALA", "32 OZ"],
      "otherProductIdentifiers": []
    }
  }
}
```

If useful OCR text isn't ready, `extraction` is omitted. Useful new text from photo OCR can request another identification pass. Late live OCR updates the item and the interface, but does not independently request refinement; it can travel with a later capture, finalization, or another identification trigger. Live camera frames are never uploaded.

The photographs preserve visual details that OCR may miss. Extracted text enters the backend visual prompt, contributes to its Exa search query, and reaches evidence resolution. For example, `OWALA` and `32 OZ` can make a generic `water bottle` query more specific. A barcode supplies another identifier to cross-check. These are implemented uses of the evidence; improved identification accuracy still needs a controlled comparison.

From here, the backend identifies the item, builds a text query for product research, and uses retrieved sources to develop the listing. Listing updates can continue after the initial identification response returns. That research process is the subject of part three.
